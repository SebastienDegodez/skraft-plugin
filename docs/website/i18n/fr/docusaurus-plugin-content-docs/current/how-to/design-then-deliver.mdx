# Concevoir, fusionner, puis livrer

Publiez l'architecture avec `skraft-design`, fusionnez sa PR, puis realisez une story avec `skraft-deliver`.
Chaque plugin s'installe seul, sans `skraft-framework` ni commande `skraft`.

:::caution[Verification native des hotes en attente]
Ces plugins sont experimentaux. Les controles locaux du moteur et du protocole ne certifient
pas une session complete Claude Code, Copilot CLI ou Azure DevOps.
:::

## Prerequis {/* #prerequisites */}

- Node 22 ou plus, Git et une branche de travail propre.
- `gh` authentifie, ou `az` avec son extension Azure DevOps, correspondant a la forge du depot.
- Une story ouverte, ou une epique ouverte contenant des stories ouvertes, pour design.
- Questions humaines natives et lancement d'agents disponibles dans l'hote.

## 2. Lancer design {/* #design */}

Demandez a l'hote d'utiliser `skraft-design` pour l'issue ou l'epique. Le design n'a pas besoin
de `skraft-design-config.json` : sa configuration demande le consentement de publication une fois
par depot et garde la reponse dans votre `~/.skraft-design/config.json`, sans rien ecrire dans la
copie de travail. La base fusionnee est la branche par defaut de la forge ; un fichier d'equipe
qui fixe `baseBranch` l'emporte.
Un brief cite chaque composant par sa racine (`services/api`) : les composants du fichier
d'equipe, sinon les projets que le run detecte dans la copie de travail. Un brief qui cite une
autre racine est refuse.

Sur GitHub, utilisez les sous-issues terminales comme stories, sans taches techniques imbriquees.
Azure DevOps conserve ses types natifs de stories.

Le moteur ecarte les stories fermees sans rien demander et les liste dans la PR d'architecture.
Chaque passe traite au plus 20 stories ouvertes. La recherche precede la conception ;
trois lentilles, un refutateur et le verdict du moteur precedent la PR d'architecture. Une passe qui
corrige des constats ou applique vos reponses tourne sur `assign.types.rework` (`standard` par
defaut), jamais au-dessus de la famille de l'architecte. Les nouveaux
ADR sont marques Accepted sur sa branche, par "architecture PR merge", et ne prennent effet que si
vous fusionnez cette PR ; aucune ratification distincte n'est demandee. Le plugin publie la PR seulement avec consentement
et conserve la recherche dans un commentaire d'issue unique, marque.

L'architecture dure par bounded context : `docs/architecture/context-map.md` avec son glossaire,
et `docs/architecture/contexts/<contexte>/` avec `tactical-design.md` et un fichier
`event-model/<tranche>.md` par tranche, reecrits en place. Les briefs d'un run sont a part dans
`docs/architecture/runs/<run>/`, pour partir ensemble une fois livres. Quand une autre branche
de design ouverte change un des memes contextes, le run demande avant de publier. La PR
d'architecture nomme chaque document partage que le run a fait depasser 15 Ko, pour que vous le
decoupiez.

Lisez chaque `docs/architecture/runs/<run>/<number>-<slug>.md` : son en-tete garde l'identite de
l'issue, l'empreinte du corps, les composants, criteres, ADR et documents communs.

### Repondre aux questions de l'architecte {/* #questions */}

Quand un choix revient au product owner, l'architecte ne s'arrete pas : il concoit le reste de la
passe sur une hypothese qu'il ecrit et laisse ses questions, chacune avec ses options et leur
consequence. Avant la revue, le run attend une seule decision qui les regroupe toutes.

- **Depuis votre editeur**, l'hote pose chaque question dans son dialogue : choisissez une option
  ou repondez avec vos mots. Toutes les reponses partent ensemble au moteur, et la conception
  repart une seule fois avec elles.
- **En CI**, copiez `plugins/skraft-design/ci/skraft-design.yml` dans `.github/workflows/`, ajoutez
  les secrets `SKRAFT_DESIGN_JOURNAL_KEY` (`openssl rand -hex 32`) et `ANTHROPIC_API_KEY`, puis
  lancez-le avec une issue ou une epique. Quand le run attend, le moteur publie une PR en brouillon
  qui liste chaque question et la reponse a recopier ; tant que rien n'est concu, comme pour une
  recherche qui ne peut pas avancer, il pose la question sur l'issue ou l'epique. Repondez en un seul
  commentaire :

```text
/skraft-answer
Q1: A
Q2: vos propres mots
```

Une question a options prend un seul mot, comme `/skraft-answer continue`. Les questions de
l'architecte acceptent aussi une reponse dans vos mots, comme `/skraft-answer B partout, on garde
le panier` : un petit agent interprete la lit quand le run reprend, le moteur ne garde sa lecture
que si elle repond a chaque question, et la PR montre ce qu'il a lu. Une reponse floue n'enregistre
rien, et la PR dit pourquoi.

Toute personne qui a le droit d'ecriture sur le depot peut repondre ; tout autre commentaire, ou
une reponse qui oublie une question, n'enregistre rien. Une story que l'architecte ne peut pas
concevoir arrete tout de suite un run CI.

## 3. Fusionner, puis livrer {/* #deliver */}

Relisez et fusionnez vous-meme la PR d'architecture. Demandez a l'hote d'utiliser `skraft-deliver`
pour une story. Sa configuration et `skraft-deliver-config.json` gardent des choix de publication,
commandes et bindings Gherkin independants. Utilisez le meme `baseBranch` que design.

Deliver lit le brief et les documents cites depuis un commit recupere de cette base fusionnee,
puis transmet leurs copies aux agents. DISTILL, revue des scenarios, validation humaine, TDD,
gates, revue d'implementation et visuels optionnels precedent la PR de livraison, qui retire
aussi le brief de la story en un commit du moteur ; git le garde, et les documents qu'il cite
restent.
Sans brief, deliver annonce son absence et fait un design leger avant DISTILL : un brief pour
la story, et un ADR seulement quand une decision le merite, que vous ratifiez avant que
DISTILL ne s'appuie dessus.

Pour reprendre, demandez au meme plugin de continuer son run actif. L'etat reste sous
`.copilot-tracking/skraft-design-runs/` ou `.copilot-tracking/skraft-deliver-runs/` ;
chacun possede son `.active-slug`. Repondez aux questions du moteur dans le dialogue natif.
Fermer ce dialogue laisse le run en pause.

## Depannage {/* #troubleshooting */}

### Deliver attend un design {/* #freshness */}

Un brief sur lequel deliver ne peut pas s'appuyer met la livraison en pause au lieu de la refuser :
`architecture-unmerged` (la PR design n'est pas encore fusionnee), `architecture-stale` (un ADR cite
n'est pas Accepted dans la base fusionnee), `architecture-invalid` (un en-tete de brief ou un
document cite est faux), ou REDESIGN a une issue modifiee, qui demande d'abord KEEP ou REDESIGN.
Corrigez-le par une PR design, fusionnez-la, revenez sur la branche de livraison et repondez
RESUME ; ou repondez CONTINUE pour livrer sur un design leger, ou STOP.

### La branche par defaut a change pendant que design attendait {/* #refresh */}

Un run de design garde la branche par defaut de son depart, sa recherche et ses composants. Si
elle a change pendant que le run vous attendait (un backend fusionne depuis, une configuration
ajoutee), repondez REFRESH : dans le meme run, sa branche reprend la branche par defaut telle
qu'elle est, les composants sont detectes a nouveau et le design repart de RESEARCH. En CI,
commentez `/skraft-answer REFRESH`. En cas de conflit, fusionnez vous-meme la branche par defaut
dans la branche du run, puis repondez REFRESH a nouveau.

### Design exclut une story {/* #readiness */}

Seules les stories ouvertes entrent dans une passe de conception ; les stories fermees sont
exclues. Une story bloquee par l'architecture exige une exclusion humaine explicite ; elle n'est
jamais abandonnee en silence.
