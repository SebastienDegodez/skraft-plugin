# DELIVER

Faire passer le contrat au vert en un seul passage et un seul commit,
puis faire relire le code. Tester les tests reste l'affaire du développeur.

## Pourquoi cette phase existe

Le code est le seul artefact qui part en production. DELIVER le fait naître du contrat que
DISTILL a laissé en échec, en un seul passage, en travaillant les groupes dans l'ordre du plan d'implémentation : le
`software-engineer` avance en **Outside-In TDD**, des tests d'acceptation du groupe vers les tests
unitaires, puis vers le code ([Freeman & Pryce, 2009](../../reference/citations.mdx#cite-freeman-goos-2009)). Il
tourne la boucle interne rouge → vert → refactor sans la commiter, puis commite une seule fois, quand
tous les groupes passent : un `feat(…)` enchaîné à la commande de test, `<test> && git add <fichiers> && git commit …`.

Le moteur ne lance aucun test. Il vérifie l'historique git : un commit rouge de chaque test
d'acceptation, puis un seul commit vert, quoi que nomme son sujet, ne touchant pas aux tests d'acceptation ; un
deuxième est refusé (`green-split`). Le tableau de groupes du plan d'implémentation est l'ordre de travail, non un nombre de commits. La commande qui commite un vert est
enchaînée à la commande de test : le commit n'existe que si les tests passent ; la revue DISTILL et
la revue DELIVER lisent le reste. Le test d'abord
([Beck, 2003](../../reference/citations.mdx#cite-beck-tdd-2003)) devient un fait dans l'historique git, pas une
promesse.

:::info[☕ Fil rouge — Starbucks *(exemple illustratif)*]

S1 et S2 entrent, rouges, à côté du walking skeleton rouge. DELIVER complète la chaîne du point
d'entrée de commande jusqu'à la base, implémente le paiement et l'attribution des points et fait
passer S1 et le walking skeleton au vert, et S2, la boisson indisponible, avec eux, en un seul commit. Les exécutions tracées de gates de l'ingénieur sont lues par la revue, qui relit aussi le code, et le code part en pull
request. Que les tests protègent réellement la règle de fidélité, la **mutation** que lance le
développeur l'atteste.
:::

## Un seul passage, un seul commit vert

Un cycle TDD commité coûte deux commits, et un agent paie chacun en tours : lancer les tests, lire
leur sortie, écrire le message. DELIVER ne commite qu'une fois pour l'histoire, et l'ingénieur livre tous les groupes en un
passage : il lit les plans et lance une fois tous les tests d'acceptation, puis travaille les groupes dans l'ordre
du plan, sans rien commiter avant que tous les tests d'acceptation et toute la suite passent. Les tests
unitaires de la boucle interne s'écrivent toujours d'abord ; ils partent dans le vert, et la
lentille test-integrity de la revue les lit. Qu'ils détecteraient une erreur, la mutation que
lance le développeur le prouve.

Trois règles gardent ce commit unique honnête :

- **Les tests d'acceptation sont un oracle immuable.** DISTILL les a écrits, walking skeleton
  compris ; le vert ne les change jamais, hors du squelette qu'ils appellent. Le vert fait passer
  tous les tests d'acceptation et le walking skeleton. Un test ajusté au code ne prouve rien, donc
  un test faux retourne à DISTILL : l'ingénieur s'arrête en le nommant.
- **Le vert ne construit que les scénarios de l'histoire.** Il n'écrit aucun comportement qu'aucun scénario ne demande,
  et ne change un autre composant que là où un groupe en a besoin.
- **Le commit suit le test.** Le brief donne la commande exacte, pour sh ou PowerShell 7 et pour
  Windows PowerShell 5.1, si bien que le commit
  n'a lieu que si les tests passent. Le rouge de DISTILL n'est jamais enchaîné ainsi : seule la
  lecture de la sortie distingue une erreur de build de l'échec attendu.

Une fois le vert commité, l'ingénieur lance les gates restantes et soumet la tentative. Un run dont le journal
contient les dispatches DELIVER par groupe d'une alpha V2 antérieure n'est pas repris : relancez-le. Un passage que renvoie la
revue travaille sur toute la story : chaque cycle est un commit `feat` ou `fix` qui
porte son test et son code, une fois vert, sans commit `test` à part.

## L'ordre : gates tracées, puis revue

<FlowFigure flow="deliver" />

Le moteur ne lance aucune gate. L'ingénieur logiciel lance chaque gate (`build`, `format`, `lint`,
`test`, `architecture`, `coverage`) de chaque composant que l'histoire a modifié par l'outil MCP
`skraft_repl` (`gate(name, command, { cwd })`, voir [Le REPL](../../reference/repl.md)) ;
l'exécution de la ligne de commit est l'exécution `test`, et une gate sans commande pour le composant
se déclare avec `absent`, comme la ligne `no command` du brief le donne. Le moteur ne refuse aucune tentative pour ces exécutions. Il journalise
`evidence.checked` pour les exécutions dont la trace se lit jusqu'à ses signatures, sinon le code de ce qui l'a cassée, et remet la trace ou ce code à la revue DELIVER
([Gates](../../reference/gates.md#command-gates)).

Viennent ensuite les lentilles de la revue DELIVER : intégrité des tests, frontières
d'architecture, lisibilité à froid, `quality-gates` et, quand le changement en touche, fidélité des mocks et des
contrats. La lentille `quality-gates` lit la trace et signale, par composant et par gate, une exécution
manquante, en échec, pas sur le dernier commit ou démarrée sur un arbre sale (hors l'exécution de la ligne de commit) ;
une gate déclarée `absent` avec une raison est acceptée, jamais `test`. Une reprise demandée par la revue repart par `deliver`. Le software engineer lance la commande e2e
d'un front end comme une gate, en dernier, sur son commit final. Après la revue, l'étape des
visuels lit ce run tracé et les captures que liste son manifeste au lieu de le lancer : sur GitHub
gh les joint à la pull request, sur Azure DevOps elles sont commitées sur la branche et liées à leur
commit. Puis viennent le `pr-writer` et la publication.

Les preuves QA du run, son plan de test, le résultat de chaque scénario et ses captures,
appartiennent au moteur : il les rend à partir du journal et de la trace dans la pull request et
`qa-report.md`. Un scénario n'est réussi que si son test d'acceptation est toujours celui de son
commit red, qu'un green a livré son groupe et que toute la suite de son composant est passée sur le
commit final ; ce qui manque n'est pas prouvé, et livré n'est pas déployé ([Joindre les preuves QA](../../how-to/attach-screenshots.md)).

### Pourquoi la mutation revient au développeur

Le mutation testing injecte de petites fautes dans le code et mesure la part que les tests
attrapent ([Jia & Harman, 2011](../../reference/citations.mdx#cite-jia-mutation-2011)). C'est la seule mesure qui
dit si une suite verte détecterait une erreur, et c'est aussi l'étape la plus coûteuse qu'une
story puisse payer.

Jusqu'à la version 2.0.0-alpha.18, elle passait juste après les gates, avant la revue, puis de
nouveau plusieurs fois. C'était l'étape la plus lente de chaque run, elle demandait une
configuration de mutation que skraft écrivait pour le développeur, et ses survivants arrêtaient le
run sur une question, tout à la fin.

Ni le pipeline de la story ni le moteur ne la lancent donc. Le mutation testing est une recette de
la session du développeur, le skill `skraft-mutation` : il lance la `commands.mutation` du composant
dans Bash, lit le rapport, juge chaque périmètre au seuil sur les fichiers que la branche a
modifiés, et tue les survivants par des tests ([Lancer la mutation](../../how-to/run-mutation.md)).
La commande peut rendre son score déjà calculé ([Le résultat de mutation](../../reference/skraft-config.md#mutation-result)).
Le seuil ne bouge pas : 80 % sur le cœur et 80 % sur la frontière, jugés à part, fixés par
`skraft-quality-bar`.

Un mutant survivant n'a toujours pas une seule bonne réponse. Il finit de l'une de trois façons :

1. **un test plus précis le tue**, parce qu'une entrée que la story autorise distingue le mutant
   du code ;
2. **le code est supprimé**, parce qu'aucun comportement de la story ne le demande ;
3. **le mutant est déclaré équivalent**, parce qu'aucune entrée ne peut le distinguer du code.

Distinguer un mutant équivalent est un problème connu pour être difficile, qu'aucun outil ne
tranche seul ([Jia & Harman, 2011](../../reference/citations.mdx#cite-jia-mutation-2011)) : le développeur
décide. Un agent à qui il demande de l'aide lit les survivants avec la skill
`quality-gates-<stack>` du composant, qui énonce chaque issue et comment neutraliser un mutant
équivalent avec sa raison.

## Les tests câblés par le même agent

Le `software-engineer` câble lui-même ses tests d'intégration, dans le scénario qu'il fait
passer : le brief que compose le moteur nomme les skills de mocking de chaque composant, et ceux
de contract testing quand le composant l'active. Sur quoi tourne chaque dépendance vient de la
[politique d'infrastructure](../../reference/skraft-config.md#infrastructure) du composant, que
suivent déjà les tests d'acceptation commités par DISTILL. Il ne lance aucun sous-agent. Quand le
changement touche un mock ou un contrat, la lentille de fidélité correspondante rejoint la
revue. Le pourquoi : [Mocking avec Microcks](../deep-dive/mocking-microcks.md)
et [Contract testing](../deep-dive/contract-testing.md).

## Les compromis

- **La boucle interne ne laisse aucune trace dans l'historique.** Seuls le rouge de l'histoire et
  son vert sont commités ; personne ne voit échouer les tests unitaires écrits entre les
  deux. La revue les juge.
- **Une story peut partir sans run de mutation.** Le pipeline ne prouve plus que les tests
  détecteraient une erreur ; le run du développeur le fait, quand il le lance.
- **Pas de seuil négociable.** 80 % sur le cœur et sur la frontière, quel que soit le dépôt :
  voir [Software craftsmanship](../software-craftsmanship.md).
