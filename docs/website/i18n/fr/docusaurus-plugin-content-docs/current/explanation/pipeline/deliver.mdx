# DELIVER

Faire passer le contrat au vert un scénario à la fois, chacun en un commit prouvé, faire relire
le code, puis tester les tests — une fois, en dernier.

## Pourquoi cette phase existe

Le code est le seul artefact qui part en production. DELIVER le fait naître du contrat que
DISTILL a laissé en échec, un scénario à la fois : le `software-engineer` avance en
**Outside-In TDD**, du test d'acceptation du scénario vers les tests unitaires, puis vers le code
([Freeman & Pryce, 2009](../../reference/citations.mdx#cite-freeman-goos-2009)). Il tourne la boucle interne
rouge → vert → refactor sans la commiter, puis commite une fois, quand le scénario passe : un
`feat(…)` enchaîné à la commande de test, `<test> && git add <fichiers> && git commit …`.

Le moteur ne croit pas l'agent sur parole. Le rouge de DISTILL a été rejoué et prouvé ; le vert de
DELIVER est rejoué aussi, et le [juge du rejeu](pathname:///dashboard/#agent-replay-judge) lit le
log du rejeu à côté de celui du rouge : les tests d'acceptation du scénario doivent y passer, et
aucun test ne doit échouer ni être sauté. Le test d'abord ([Beck, 2003](../../reference/citations.mdx#cite-beck-tdd-2003)) devient un fait dans
l'historique git, pas une promesse : pour chaque scénario, un commit rouge de son test
d'acceptation, puis un commit vert.

:::info[☕ Fil rouge — Starbucks *(exemple illustratif)*]

S1 entre, rouge. DELIVER implémente le paiement et l'attribution des points et le fait passer au
vert en un commit ; DISTILL écrit ensuite le test en échec de S2, la boisson indisponible, et
DELIVER le fait passer au vert. Les gates passent, la revue relit le code, puis la **mutation**
atteste que les tests protègent réellement la règle de fidélité. Le code part en pull request.
:::

## Un scénario, un commit vert

Un cycle TDD commité coûte deux commits, et un agent paie chacun en tours : lancer les tests, lire
leur sortie, écrire le message. Par scénario, DELIVER ne commite qu'une fois. Les tests
unitaires de la boucle interne s'écrivent toujours d'abord ; ils partent dans le vert, et la
mutation, lancée en dernier sur toute la story, prouve qu'ils détecteraient une erreur.

Trois règles gardent ce commit unique honnête :

- **Les tests d'acceptation sont un oracle immuable.** DISTILL les a écrits ; le vert ne les
  change jamais, hors du squelette qu'ils appellent. Un test ajusté au code ne prouve rien, donc
  un test faux retourne à DISTILL : l'ingénieur s'arrête en le nommant.
- **Un scénario appartient à un seul composant.** Son vert ne change aucun autre composant ; un
  changement nécessaire ailleurs est un scénario qui manque.
- **Le commit suit le test, en bash.** Le brief donne la commande exacte, si bien que le commit
  n'a lieu que si les tests passent. Le rouge de DISTILL n'est jamais enchaîné ainsi : seule la
  lecture de la sortie distingue une erreur de build de l'échec attendu.

Une fois le dernier scénario au vert, les gates passent. Un passage que renvoient les gates ou la
revue travaille sur toute la story avec le cycle classique : un rouge, puis la correction ; sur un
passage que les gates ont renvoyé, leur échec tient lieu du rouge.

## L'ordre : gates, revue, puis mutation

<FlowFigure flow="deliver" />

Les gates de commandes passent d'abord : elles sont rapides, déterministes, et un build rouge
n'a pas besoin d'un relecteur. Viennent ensuite les lentilles de la revue DELIVER : intégrité des
tests, frontières d'architecture, lisibilité à froid, et, quand le changement en touche, fidélité
des mocks et des contrats. Une reprise demandée par la revue repart par `deliver` et les gates,
jamais par la mutation.

L'engineer lance les mêmes commandes avant de rendre la main. Son brief liste les commandes de
gates de chaque composant qu'il peut modifier, mutation exclue, avec la base du run à la place de
`{baseSha}`, et lui demande de corriger chaque échec avant d'écrire son résultat, à une passe de
reprise aussi. L'étape des gates reste le contrôle ; le brief évite la passe que coûterait un
échec de format ou de build découvert là seulement.

### Pourquoi la mutation passe en dernier

Le mutation testing injecte de petites fautes dans le code et mesure la part que les tests
attrapent ([Jia & Harman, 2011](../../reference/citations.mdx#cite-jia-mutation-2011)). C'est la seule mesure qui
dit si une suite verte détecterait une erreur, et c'est aussi l'étape la plus coûteuse du
pipeline.

Jusqu'à la version 2.0.0-alpha.18, elle passait juste après les gates, avant la revue. Elle
tournait donc plusieurs fois : après chaque passe de correction des survivants, puis de nouveau
après chaque reprise demandée par la revue — et elle jugeait un code que cette revue pouvait
encore faire changer. Depuis 2.0.0-alpha.19, elle passe **une fois, en dernier**, sur le code
que la revue a approuvé. Sur le chemin normal, la mesure la plus chère ne tourne qu'une fois, et
elle mesure le code qui partira réellement.

### Pourquoi c'est le développeur qui choisit

Un mutant survivant n'a pas une seule bonne réponse. Il finit de l'une de trois façons :

1. **un test plus précis le tue**, parce qu'une entrée que la story autorise distingue le mutant
   du code ;
2. **le code est supprimé**, parce qu'aucun comportement de la story ne le demande ;
3. **le mutant est déclaré équivalent**, parce qu'aucune entrée ne peut le distinguer du code.

Ces trois issues n'ont pas les mêmes conséquences : la première ajoute une protection, la
deuxième retire du code, la troisième accepte un écart. Distinguer un mutant équivalent est un
problème connu pour être difficile, qu'aucun outil ne tranche seul
([Jia & Harman, 2011](../../reference/citations.mdx#cite-jia-mutation-2011)). Laisser un agent « tuer les mutants »
à sa guise l'invite à écrire des tests taillés pour le mutant plutôt que pour un comportement.

Alors la décision est partagée. Pour chaque fichier qui garde des survivants, le
`software-engineer` écrit une **proposition** dans un fichier que le moteur crée, une issue par
mutant, sans toucher au code. La question `mutation-plan` montre ces propositions au développeur,
qui répond `APPLY`, donne sa propre consigne, ou `STOP`. Le `software-engineer` applique ensuite
ce choix en un seul passage ; la lentille `test-integrity` relit les tests ajoutés, les gates
repassent, puis la mutation de nouveau.

Le seuil, lui, ne bouge pas : la gate `mutation` reste verrouillée et sa barre fixe. Le
développeur choisit **comment** l'atteindre, jamais **s'il** faut l'atteindre.

## Les tests câblés par le même agent

Le `software-engineer` câble lui-même ses tests d'intégration, dans le scénario qu'il fait
passer : le brief que compose le moteur nomme les skills de mocking de chaque composant, et ceux
de contract testing quand le composant l'active. Sur quoi tourne chaque dépendance vient de la
[politique d'infrastructure](../../reference/skraft-config.md#infrastructure) du composant, que
suivent déjà les tests d'acceptation commités par DISTILL. Il ne lance aucun sous-agent. Quand le
changement touche un mock ou un contrat, la lentille de fidélité correspondante rejoint la
revue. Le pourquoi : [Mocking avec Microcks](../deep-dive/mocking-microcks.md)
et [Contract testing](../deep-dive/contract-testing.md).

## Les compromis

- **La boucle interne ne laisse aucune trace dans l'historique.** Seuls le rouge et le vert de
  chaque scénario sont commités ; personne ne voit échouer les tests unitaires écrits entre les
  deux. La mutation et la revue les jugent.
- **Un humain peut être sollicité en fin de run.** Quand la mutation échoue, le run attend la
  réponse à `mutation-plan`. C'est le prix d'une décision qui engage le code.
- **Une reprise de revue ne remesure pas la mutation.** Elle repasse par les gates, plus
  rapides ; la mutation juge une fois le code stabilisé.
- **Pas de seuil négociable.** 100 % sur le cœur, 80 % sur la frontière, quel que soit le dépôt :
  voir [Software craftsmanship](../software-craftsmanship.md).
