# Design, merge, then deliver

Publish architecture with `skraft-design`, merge its PR, then implement a story with `skraft-deliver`.
Each plugin installs alone; neither requires `skraft-framework` or the `skraft` command.

:::caution[Native host verification pending]
These plugins are experimental. Local engine and protocol checks do not certify a complete
Claude Code, Copilot CLI or Azure DevOps session.
:::

## Prerequisites {/* #prerequisites */}

- Node 22 or later, Git and a clean working branch.
- An authenticated `gh`, or `az` with its Azure DevOps extension, matching the repository forge.
- An open story, or an open epic containing open stories, for design.
- Native human questions and agent dispatch supported by the host.

## 2. Run design {/* #design */}

Ask the host to use `skraft-design` for the issue or epic. Design needs no
`skraft-design-config.json`: its setup asks publication consent once per repository and keeps
the answer in your own `~/.skraft-design/config.json`, writing nothing in the working copy. The
merged base is the forge's default branch; a team file that sets `baseBranch` overrides it.
A brief cites each component by its root (`services/api`): the team file's components, else the
projects the run detects in the working copy. A brief citing any other root is refused.

On GitHub, use terminal sub-issues as stories; do not nest technical tasks under them.
Azure DevOps keeps its native story types.

The engine leaves closed stories out without asking and lists them in the architecture PR. Each design pass
handles at most 20 open stories. Research precedes design; three review lenses, a refuter and
the engine verdict precede the architecture PR. A pass that fixes findings or applies your answers
runs on `assign.types.rework` (`standard` by default), never above the architect's own family. New ADRs are marked Accepted on its branch, by
"architecture PR merge", and take effect only when you merge that PR; no separate ADR
ratification is asked. The plugin publishes
the architecture PR only with consent, and keeps research in one marked issue comment.

The architecture lasts by bounded context: `docs/architecture/context-map.md` with its glossary,
and `docs/architecture/contexts/<context>/` with `tactical-design.md` and one
`event-model/<slice>.md` per slice, rewritten in place. A run's briefs sit apart in
`docs/architecture/runs/<run>/`, so they go together once delivered. When another open design
branch changes one of the same contexts, the run asks before it publishes. The architecture PR
names each shared document the run changed past 15 KB, so you split it.

Read each `docs/architecture/runs/<run>/<number>-<slug>.md`: its header records the issue identity,
body fingerprint, components, criteria, ADRs and shared documents.

### Answer the architect's questions {/* #questions */}

When a choice belongs to the product owner, the architect does not stop: it designs the rest of
the pass on a stated assumption and leaves its questions, each with its options and their
consequence. Before the review, the run waits on one decision that holds them all.

- **From your editor**, the host asks each question in its chat: pick an option or answer in your
  own words. Every answer reaches the engine at once, and design runs again once with them.
- **In CI**, copy `plugins/skraft-design/ci/skraft-design.yml` into `.github/workflows/`, add the
  secrets `SKRAFT_DESIGN_JOURNAL_KEY` (`openssl rand -hex 32`) and `ANTHROPIC_API_KEY`, then run it
  with an issue or an epic. A committed `skraft-design-config.json` holds no `publish`: it is read
  over the workflow's consent, and its `"pullRequest": false` would stop every pull request. When
  the run waits, the engine publishes a draft pull request and asks
  each question in a comment of its own there, with the reply to copy; while nothing is designed
  yet, such as a researcher that cannot go on, it asks in a comment on the issue or epic instead.
  A new question never rewrites an earlier one: once answered, its comment says what was
  recorded, and the pull request lists every answer. Once the design is done, the draft becomes a
  pull request ready for review. Answer in one comment:

```text
/skraft-answer
Q1: A
Q2: your own words
```

A question with options takes one word, such as `/skraft-answer continue`. The architect's
questions also take a reply in your own words, such as `/skraft-answer B everywhere, keep the
basket`: a small interpreter agent reads it when the run resumes, the engine keeps its reading only
when it answers every question, and the pull request shows what it read. An unclear reply answers
nothing, and the pull request says why.

Anyone with write access to the repository may answer; any other comment, or a reply that leaves
a question out, records nothing. A story the architect cannot design stops a CI run at once.

## 3. Merge, then deliver {/* #deliver */}

Review and merge the architecture PR yourself. Ask the host to use `skraft-deliver` for one story.
Its separate setup and `skraft-deliver-config.json` preserve independent publication choices,
commands and Gherkin bindings. Use the same `baseBranch` as design.

To deliver in CI, copy `plugins/skraft-deliver/ci/skraft-deliver.yml` into `.github/workflows/`,
commit `skraft-deliver-config.json` with the project's components, add the secrets
`SKRAFT_DELIVER_JOURNAL_KEY` and `ANTHROPIC_API_KEY`, and add the steps that install the project's
toolchain where the file says so: the agents never install one. For a Java 21 project built with
Maven, for instance:

```yaml
- uses: actions/setup-java@<commit> # pin the release you trust
  if: github.event_name == 'workflow_dispatch' || steps.target.outputs.branch != ''
  with:
    distribution: temurin
    java-version: '21'
    cache: maven
```

Run it with a story: each question
is asked in a comment of its own, on the story, then on the draft pull request (the light design
to ratify, the scenarios and their red), and answered with `/skraft-answer`, such as
`/skraft-answer REVISE mail the receipt from orders`.

Delivery reads the brief and cited documents from one fetched commit of that merged base,
then supplies snapshots to its agents. DISTILL, scenario review, human approval, TDD,
gates, implementation review and optional visuals precede the delivery PR, which also removes
the story's brief in one engine commit; git keeps it, and the documents it cites stay.
Without a brief, delivery announces its absence and runs a light design before DISTILL: one
brief for the story, and an ADR only when a decision deserves one, which you ratify before
DISTILL relies on it.

Resume by asking the same plugin to continue its active run. State stays under
`.copilot-tracking/skraft-design-runs/` or `.copilot-tracking/skraft-deliver-runs/`;
each uses its own `.active-slug`. Answer engine questions through native chat.
Dismissal leaves the run paused.

## Troubleshooting {/* #troubleshooting */}

### Delivery waits for a design {/* #freshness */}

A brief delivery cannot rely on pauses the delivery instead of refusing it:
`architecture-unmerged` (the design PR is not merged yet), `architecture-stale` (a cited ADR is
not Accepted in the merged base), `architecture-invalid` (a brief header or cited document is
wrong), or REDESIGN to a changed issue, which asks KEEP or REDESIGN first. Fix it through a design
PR, merge it, check out the delivery branch again and answer RESUME; or answer CONTINUE to deliver
on a light design, or STOP.

### The default branch moved while design waited {/* #refresh */}

A design run keeps the default branch it started from, its research and its components. When the
branch moved while the run waited on you (a back end merged since, a configuration added), answer
REFRESH: in the same run, its branch takes the default branch as it is now, the components are
detected again and the design starts again from RESEARCH. In CI, comment `/skraft-answer REFRESH`.
On a merge conflict, merge the default branch into the run's branch yourself, then answer REFRESH
again.

### Design excludes a story {/* #readiness */}

Only open stories enter a design pass; closed stories are excluded. Architecture-blocked stories
need explicit human exclusion; they are never silently dropped.
