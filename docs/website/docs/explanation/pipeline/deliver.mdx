# DELIVER

Turn the contract green one scenario at a time, each in one proven commit, have the code
reviewed, then test the tests — once, last.

## Why this phase exists

Code is the only artifact that goes to production. DELIVER grows it from the contract DISTILL
left failing, one scenario at a time: the `software-engineer` works in **Outside-In TDD**, from
the scenario's acceptance test to the unit tests, then to the code
([Freeman & Pryce, 2009](../../reference/citations.mdx#cite-freeman-goos-2009)). It runs the inner red → green →
refactor loop without committing it, then commits once, when the scenario passes: a `feat(…)`
chained to the test command, `<test> && git add <files> && git commit …`.

The engine does not take the agent's word for it. DISTILL's red was replayed and proven; DELIVER's
green is replayed too, and the [replay judge](pathname:///dashboard/#agent-replay-judge) reads
the replay's log next to the red's: the scenario's acceptance tests must pass at it, and no test
may fail or be skipped.
Test first ([Beck, 2003](../../reference/citations.mdx#cite-beck-tdd-2003)) becomes a fact in the git history, not a
promise: for each scenario, a red commit of its acceptance test, then a green commit.

:::info[☕ Running example — Starbucks *(illustrative)*]

S1 enters, red. DELIVER implements payment and loyalty crediting and turns it green in one
commit; DISTILL then writes the failing test of S2, the unavailable drink, and DELIVER turns it
green. The gates run, the review reads the code, then **mutation** shows the tests genuinely
protect the loyalty rule. The code goes into a pull request.
:::

## One scenario, one green commit

A committed TDD cycle costs two commits, and an agent pays each one in turns: running the tests,
reading their output, writing the message. Per scenario, DELIVER commits once. The unit tests
of the inner loop are still written first; they go into the green, and mutation, run last on the
whole story, is what proves they would catch a mistake.

Three rules keep that single commit honest:

- **The acceptance tests are an immutable oracle.** DISTILL wrote them; the green never changes
  them, outside the skeleton they call. A test fitted to the code proves nothing, so a wrong test
  goes back to DISTILL: the engineer stops, naming it.
- **A scenario belongs to one component.** Its green changes no other component; a change needed
  elsewhere is a missing scenario.
- **The commit follows the test, in bash.** The brief gives the exact command, so the commit
  happens only when the tests pass. DISTILL's red is never chained that way: only reading the
  output tells a build error from the expected failure.

Once the last scenario is green, the gates run. A pass the gates or the review send back works on
the whole story with the classic cycle: a red, then the fix; on a pass the gates sent back, their
failure stands for the red.

## The order: gates, review, then mutation

<FlowFigure flow="deliver" />

The command gates run first: they are fast, deterministic, and a red build needs no reviewer.
Then come the DELIVER review's lenses: test integrity, architecture boundaries, cold reading,
and, when the change touches them, mock and contract fidelity. A rework the review asks for goes
back through `deliver` and the gates, never through mutation.

The engineer runs the same commands before it hands over. Its brief lists the gate commands of
each component it may change, mutation left out, with the run's base in place of `{baseSha}`, and
tells it to fix every failure before it writes its result, on a rework pass too. The gates step
stays the check; the brief saves the pass that a format or build failure found only there would
cost.

### Why mutation runs last

Mutation testing injects small faults into the code and measures how many the tests catch
([Jia & Harman, 2011](../../reference/citations.mdx#cite-jia-mutation-2011)). It is the only measure that tells
whether a green suite would detect a mistake, and it is also the most expensive step of the
pipeline.

Up to version 2.0.0-alpha.18 it ran right after the gates, before the review. So it ran several
times: after each pass fixing survivors, then again after each rework the review asked for — and
it judged code that review could still change. Since 2.0.0-alpha.19, it runs **once, last**, on
the code the review approved. On the normal path, the most expensive measure runs once, and it
measures the code that will actually ship.

### Why the developer chooses

A surviving mutant has no single right answer. It ends one of three ways:

1. **a sharper test kills it**, because an input the story allows tells the mutant from the
   code;
2. **the code is deleted**, because no behaviour of the story asks for it;
3. **the mutant is declared equivalent**, because no input can tell it from the code.

These three outcomes do not have the same consequences: the first adds protection, the second
removes code, the third accepts a gap. Telling an equivalent mutant apart is a known hard
problem no tool settles on its own ([Jia & Harman, 2011](../../reference/citations.mdx#cite-jia-mutation-2011)).
Letting an agent "kill the mutants" as it sees fit invites tests tailored to the mutant rather
than to a behaviour.

So the decision is shared. For each file that keeps survivors, the `software-engineer` writes a
**proposal** in a file the engine creates, one outcome per mutant, without touching the code. The
`mutation-plan` question shows those proposals to the developer, who answers `APPLY`, gives their
own instruction, or `STOP`. The `software-engineer` then applies that choice in a single pass;
the `test-integrity` lens reviews the tests added, the gates run again, then mutation again.

The bar itself does not move: the `mutation` gate stays locked and its threshold fixed. The
developer chooses **how** to reach it, never **whether** to.

## Tests wired by the same agent

The `software-engineer` wires its own integration tests, inside the scenario it makes pass: the
brief the engine composes names each component's mocking skills, and the contract-testing ones
when the component turns it on. What each dependency runs on comes from the component's
[infrastructure policy](../../reference/skraft-config.md#infrastructure), which the acceptance
tests DISTILL committed already follow. It starts no sub-agent. When the change touches a mock or a
contract, the matching fidelity lens joins the review. The why:
[Mocking with Microcks](../deep-dive/mocking-microcks.md) and
[Contract testing](../deep-dive/contract-testing.md).

## Trade-offs

- **The inner loop leaves no trace in the history.** Only each scenario's red and green are
  committed; nobody sees the unit tests written in between fail. Mutation and the review judge them.
- **A human may be asked at the end of the run.** When mutation fails, the run waits for the
  answer to `mutation-plan`. That is the price of a decision that commits the code.
- **A review rework does not re-measure mutation.** It goes back through the faster gates;
  mutation judges the code once it has settled.
- **No negotiable threshold.** 100 % on the core, 80 % on the boundary, whatever the repository:
  see [Software craftsmanship](../software-craftsmanship.md).
