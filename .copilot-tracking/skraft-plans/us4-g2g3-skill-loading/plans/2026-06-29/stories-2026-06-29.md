## Design Decisions — 3 Open Questions Resolved

> These resolutions unblock DESIGN. Each decision is binding for the implementation plan.

### DD-1 — Transcript payload structure at SubagentStop

**Question:** Does Claude Code provide the SubagentStop transcript inline in the hook payload, via a temp file path, or not at all?

**Research evidence:**
- `transcript-reader.mjs` port stub: `{ read(): Promise<string> }` — no arguments. The adapter must close over the payload at construction time.
- `payload.mjs` normalizer recursively camelCases ALL nested objects/arrays — including any `transcript` field.
- Hook test `service.handle({ hookType: 'SubagentStop' })` passes no transcript — the runtime does not guarantee its presence.
- Port design (no-arg `read()`) is consistent with a factory-per-invocation pattern: the adapter receives the payload at construction, not at `read()` time.

**Decision:**
The transcript is provided as `payload.transcript` (array of message objects, already normalized) when the Claude Code runtime includes it. The adapter `jsonl-transcript-reader.mjs` is a per-invocation factory:

```
createJsonlTranscriptReader({ transcript }) → { read(): Promise<string> }
```

- `read()` returns `JSON.stringify(transcript)` when `transcript` is a non-empty array.
- `read()` throws `new Error('TRANSCRIPT_UNAVAILABLE')` when `transcript` is absent or empty.
- `subagent-stop-service` catches this error, emits a WARN JSONL audit entry (`reason: 'transcript_unavailable'`), and returns `allow` (explicit fail-open policy).
- **G2 block applies ONLY when transcript is successfully read AND a mandatory skill is confirmed absent.**

No shell/filesystem calls required. The transcript content lives in the normalized payload.

### DD-2 — PostToolUse `Read` matcher scope

**Question:** Should the `SKILL.md`-read filter live at manifest level (hooks.json `matcher`) or service level (path filter in post-tool-use-service)?

**Decision:**
Two-level filter:
1. **Manifest level** (`hooks.json`): add a second `PostToolUse` entry with `matcher: "Read"`. This fires the hook for ALL `Read` tool events.
2. **Service level** (`post-tool-use-service.mjs`): filter by path suffix. Only process events where `payload.toolInput?.path` matches the regex `/\/SKILL\.md$/`. Non-matching Read events return `allow` immediately without writing any audit entry.

This is the established SKRAFT pattern (coarse manifest, fine service). The existing `PostToolUse Agent` entry (for future G6) is NOT modified.

```json
{
  "type": "command",
  "command": "node \"${CLAUDE_PLUGIN_ROOT}/src/cli/hook.mjs\" PostToolUse Read",
  "matcher": "Read"
}
```

---

### DD-3 — Eager mode definition

**Question:** Which agents / which skills trigger eager (inline SKILL.md content) vs verify (directive only)?

**Decision:**
Eager mode is per-skill, declared via the existing `policy` field in `agentSkills`:

- `policy: 'verify'` (default) → emit `additionalContext` with text directive naming mandatory skills.
- `policy: 'eager'` → additionally read the SKILL.md file content from filesystem (via injected `skillFileReader` port) and inline it in `additionalContext`.

Fail-open for eager: if SKILL.md cannot be read, fall back to verify-style directive and emit a WARN audit entry. The `additionalContext` decision is always returned (never blocks on eager-mode failure).

**API shape:**
```
createSubagentStartService({ config, skillFileReader, auditWriter, clock })
  .handle({ agentName })  → Promise<HarnessDecision>
```

No new config schema needed — the existing `{ name, policy }` shape in `agentSkills` is sufficient.

## Story

> As a **SKRAFT pipeline operator** `[PERSONA INFERRED — the human who launches a SKRAFT run and needs confidence that every agent operates with its domain knowledge loaded]`,
> I want **every agent to be forced to load its mandatory skills at the start of its session, to be blocked and restarted if a mandatory skill was never read, and to have every skill read logged as an immutable JSONL audit entry**,
> so that **no agent ever silently drifts from its documented behaviour due to a missing skill, the pipeline surfaces the failure immediately rather than producing drifted artefacts, and I can audit skill-loading compliance for any completed run**.

### Problem Statement

When a SKRAFT agent starts, nothing currently forces it to read its mandatory skills. An agent can silently skip its skills, run on raw model knowledge, and produce artefacts that diverge from the documented SKRAFT process. This failure mode is:
- **Invisible** — the pipeline succeeds; the artefacts look plausible; the drift is only caught in review (or not at all).
- **Expensive** — subsequent phases consume drifted artefacts and produce downstream drift, multiplying token cost.
- **Unauditable** — no record exists of which skills were read (or skipped) per run.

## Domain Examples

Config: `agentSkills["backlog-planner"] = [{ name: "issue-refinement", policy: "verify" }, { name: "sprint-planning", policy: "verify" }]`

1. **G2 directive inject (verify mode)** — `backlog-planner` starts → `additionalContext`: "The following skills are MANDATORY: issue-refinement, sprint-planning."
2. **G2 block — mandatory skill never read** — `backlog-planner` finishes; transcript has `Read(sprint-planning/SKILL.md)` but NOT `issue-refinement` → `block`: "Mandatory skill not loaded: issue-refinement."
3. **G2 allow — all mandatory skills read** — `solution-architect` finishes; transcript has `Read(architecture-decisions/SKILL.md)`, `Read(architecture-patterns/SKILL.md)` → `allow`.
4. **G2 eager mode** — `acceptance-designer` starts; `bdd-methodology` has `policy: 'eager'` → SKILL.md content inlined in `additionalContext` alongside mandatory directive.
5. **G3 audit — SKILL.md read logged** — `solution-architect` reads `architecture-decisions/SKILL.md` → JSONL: `{ eventType: "SkillRead", agentName: "solution-architect", skillName: "architecture-decisions", path: "...", timestamp: "..." }`.
6. **G3 audit fail-open** — `post-tool-use-service` fails to write JSONL (I/O error) → `allow`; agent not blocked.
7. **G2 fail-open — transcript unavailable** — `backlog-planner` stops; `payload.transcript` absent → WARN audit (`reason: 'transcript_unavailable'`) + `allow`.
8. **G3 non-skill read ignored** — `software-engineer` reads `src/application/pre-tool-use-service.mjs` → path does not end with `SKILL.md` → `allow` immediately, no audit entry.

### AC-02 — At SubagentStop, an agent that skipped a mandatory skill is blocked and restarted

```gherkin
Given an agent with mandatory skills [skill-A, skill-B] declared in config

And the agent's session transcript does NOT contain a read of skill-A's skill definition file
When the agent stops its session (SubagentStop event fires)
Then the hook returns block naming the unread mandatory skill (skill-A)
And the block decision is recorded in the JSONL audit log with the agent name, the missing skill name, and a timestamp
```

### AC-04 — Every SKILL.md read is traced as a JSONL audit entry (fail-open)

```gherkin

```

Traces issue AC4. Covers domain examples 5, 6, 8.

## Non-Functional Requirements

| Category | Requirement |
|---|---|
| **Performance** | `subagent-start-service` and `subagent-stop-service` complete within 200 ms for agents with ≤ 20 mandatory skills. No synchronous I/O on the critical path. |
| **Observability** | Every G2 decision (allow/block) and every G3 skill read are written to JSONL with: `eventType`, `agentName`, `skillName` (or `missingSkill`), `path` (G3), `decision`, `timestamp` (ISO-8601). Fail-open on audit write — agent never blocked by audit failure. |
| **Security** | Transcript content (`payload.transcript`) is read-only; adapter must not write back to payload. Path matching uses suffix regex `/\/SKILL\.md$/` to prevent path-traversal false positives. Skill file reads (eager mode) scoped to plugin root — no absolute path injection from config. |
| **Reliability** | All three services are fail-open: G3 uncaught exception → `allow`; transcript read failure in G2 → `allow` + WARN audit; eager filesystem read failure → verify directive + WARN audit. |
| **Testability** | All services are pure functions of injected ports (no direct filesystem/JSONL calls in application layer). Each service independently testable with in-memory doubles. |

## Technical Notes (for DESIGN/DELIVER)

- **Naming:** `domain/skill-policy.mjs` is the runtime module. Do NOT conflate with `domain/dispatch-policy.mjs` (build-time invariant, different lifecycle, different signature).
- **Purity:** `skill-policy.mjs` must be pure — no IO. `mandatorySkillsFor(agentName, config)` reads `config.agentSkills[agentName]`; `missingSkills(readPaths, required)` performs set subtraction.
- **Transcript regex:** `subagent-stop-service` must match skill paths across all declared skill roots. Pattern: `/(?:plugins\/skills|\.agents\/skills|\.github\/skills|\.copilot\/skills)\/([^/]+)\/SKILL\.md$/i`. Capture group 1 = skill name.
- **hook.mjs composition:** both #49 and #50 update `plugins/skraft-framework/src/cli/hook.mjs`. Implement #49 first; #50 adds to the same composition root.
- **hooks.json:** existing `PostToolUse Agent` entry (future G6) must NOT be modified. Add a new, separate `PostToolUse Read` entry.
- **Config source:** `agentSkills` from generated `plugins/skraft-framework/skraft-framework.config.json` (#48). Never hardcode agent names or skill lists.
- **Test pattern:** boundary-to-boundary tests at hook gates. Reuse `jsonl-audit-writer.mjs` as audit sink. Follow `pre-tool-use-service` test pattern (in-memory doubles).
- **Reference:** `.specs/plans/2026-06-20-skraft-framework-guardrails-plan.md` Task 4 == this US.
